# 基础设施拓扑展示契约

## 目标

`/infrastructure` 不是资产示意图，而是网管实际服务调用关系的可视化入口。图中的状态、链路、端口和安全说明由 233 BFF 的 `/api/netops2026/infrastructure/snapshot` 提供；前端不得自行猜测服务器可达性或防火墙策略。

## 固定分层

```text
用户浏览器 / 受控内网
        │ HTTPS 5772
        ▼
233 统一网管（Nginx → Vue SPA / Flask BFF）
 ├── HTTP 18086、MySQL 3339 ──► 236 采集与查询
 ├── HTTP + 服务签名 18080 ──► 20 AIOps
 └── ClickHouse HTTP 8123 ────► 212 历史分析

NAS / BRAS 镜像 ── UDP 1812 / 1813 / 3799 ──► 213 Radius Monitor
213 Radius Monitor ── ClickHouse HTTP 8123 ───► 212
```

入口只能标记为 **`233:5772`**。`7001` 是 233 的回环 BFF 监听端口，不是浏览器入口；旧 `/wx/*` 路由仅保留 410 退役响应，不能出现在主拓扑。

## 本次重画解决的问题

旧图把入口标为 `80/443`，并把 NAS/BRAS、233 平台和所有服务节点散布在同一平面，造成“谁调用谁”和数据流方向难以辨认；链路标签又与曲线交叉，阅读时容易误把 Radius 数据流当成采集或数据库调用。

新版以 `5772` 用户入口置顶、233 平台居中、四个服务节点横向排列于底部；Radius 镜像源作为独立左侧输入，仅连接 213。每条链路的协议/端口只出现一次，选中后在下方统一展示安全策略，避免卡片因说明文字长短而高低不齐。

## 视觉与交互规则

1. 用“入口 → 平台中枢 → 服务域”三层布局，避免把所有节点围绕中心随机散布。
2. 每条链路只显示一次方向、协议和端口；数据流动画沿真实调用方向运行。
3. 节点仅显示名称、主机标识、健康状态和最多三个关键服务；点击后再展开服务、资源、端口和日志入口，避免卡片高低不齐。
4. 绿色代表已探测正常，黄色代表资源/服务关注，红色代表探测失败；“待审计/待收紧”使用风险说明，不伪装成健康状态。
5. 移动端改为纵向分层列表；不显示缩小后不可读的 SVG 连线。

## 安全状态必须如实展示

| 链路/节点 | 展示口径 |
| --- | --- |
| 233 入口 | UFW 对外暴露 `5772`；BFF `7001` 仅回环；SSH 有 Fail2ban |
| 233 → 236 | 236 已有 SSH Fail2ban，但主机入站白名单尚未实施；`18086/3339` 应显示“待收紧” |
| 233 → 20 | 20 端口守卫限制 `18080/18190` 为 233/本机；SSH 有 Fail2ban |
| NAS/BRAS → 213 | 213 的 `3306/18190` 有端口守卫；Radius UDP 镜像来源需按 NAS/BRAS 清单复核 |
| 233/236/213 → 212 | 212 端口守卫仅允许这三个业务节点和本机访问 `8123`；SSH `5334` 仅允许 `172.31.0.0/16`；`9000/9004/9005/9009` 仅本机；SSH Fail2ban 已启用 |

## 验证清单

```bash
npm ci
npm run build
```

部署后验证：

1. `https://anbo.njcatv.net:5772/infrastructure` 能加载；
2. 页面及详情中无 `wx`、`7001` 浏览器入口或过期端口；
3. `233:5772`、`236:18086/3339`、`20:18080`、`213 UDP 1812/1813/3799`、`212:8123` 均可见；
4. 至少点击一个节点和一个链路，确认详情来自 BFF 快照而非硬编码状态。
